See the [announcement](/posts/2026-11-21/) for context, but TLDR: this is a catch-up devblog-style post on where I am with Lookout, which is currently at `V1 alpha1`. Today we'll focus on how I got real GPS samples from a train.

<!-- more -->

I go to Germany every year, and had been planning to visit a few places in the area around Mannheim, so this was a good opportunity to get a sense of what real experience on a train would look like. [One of the very first things](https://github.com/mikemoraned/geo/blob/main/apps/lookout/docs/completed-slices.md#mike-is-on-a-train-getting-data) I did was to start recording real GPS traces. This was done via a website running on iPad/iPhone using local sensors → saving to an online Redis queue (`landing`) → draining into `bronze` for later analysis (note, see further below for `landing`/`bronze` explanation).

{{ image(src="/images/lookout/laptop-ipad-on-train.png", alt="initial version of Lookout being developed on train, and recording GPS data") }}

The GPS data from my phone wasn't too surprising: I know from using other Apps that it can vary a lot in accuracy. However, I know an iPhone does some fairly clever stuff behind the scenes, so what would it be like on other types of devices? 

I'd already [been playing around](https://github.com/mikemoraned/blescan/tree/m5/m5) with some [M5 devices](https://m5stack.com), and so had some to develop on. As a way to keep this real, and not coupled to Apple devices, I adopted a requirement that anything I build must be able to run on an [M5 device](https://shop.m5stack.com/products/m5stickc-plus2-esp32-mini-iot-development-kit?variant=44269818216705) with an [attached GPS sensor](https://shop.m5stack.com/products/gps-bds-unit-v1-1-at6668?variant=45727253692673), as well as on a website on an iPhone.

{{ image(src="/images/lookout/m5-gps-on-bag.png", alt="M5 and GPS device sitting on bag") }}

The ultimate V1 App should still be able to do "opportunistic enrichment", if extra capabilities are available, but the core features should always work on an M5 device where the only connectivity it has is passive GPS.

It is totally ok, however, to do a bunch of processing offline ahead of time. This is where I adopted the ["Medallion Pattern"](https://github.com/mikemoraned/geo/blob/main/apps/lookout/docs/medallion.md), instantiated here roughly as:
* `landing`: device recordings, and other raw data, typically in a non-parquet native format, focussed on being easy to capture and not kept long-term,
* → `bronze`: similar data as landing, but in parquet format and persisted + also snapshots of external datasets,
* → `silver`: normalised and processed derived data, based on what's in bronze,
* → `gold`: distilled and minimised versions of silver data, targeted for deployment on the devices themselves.

(We'll return to this processing pipeline in future posts.)

Getting things working on the M5 wasn't simple, as there is a lot to discover about device setup. This was actually where using Claude was super-useful as I am *far* less of an expert in ESP32 device stuff than in everything else I've mentioned so far. The user-friendliness of the M5 stack also came in handy: it was super-easy to get it powered-up and talking serial over the USB cable. So, this made for quite a fruitful and tight dev loop, particularly when I could test the GPS whilst on a live train.

Having to test outside in my garden was somewhat colder and less comfortable.

{{ image(src="/images/lookout/testing-in-garden-in-ed.png", alt="Testing in Garden, outside in Edinburgh") }}

{% aside() %}
Btw, for the rest of this devblog, I will refer to Claude in the same way as above, i.e., when it made a significant difference, I'll mention it. I've used Claude for the vast majority of the work here, but I've made a point of only committing things I personally understand or at least have driven very deliberately.

I know that, given my personal time constraints, this project wouldn't be where it is without using it, but that's more of a credit to the many billions of lines of text that went into Claude's training datasets. Similarly, I would still be grovelling around for clean data if I hadn't started using [Overture Maps last year](/posts/2025-06-17/)!

I don't wanna hide that I've used it extensively, but I also don't wanna start treating this as a "we did this" project; "I" did this on the shoulders of many other *people*.
{% end %}

Where does this get us? It gets us to a dataset which I've subsequently used repeatedly to ground various decisions in actual recorded data, and proof that the GPS data can be gotten on multiple device types.
