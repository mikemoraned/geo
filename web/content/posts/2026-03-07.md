Like [before](/posts/2025-12-26/), this was another question that came up over the dinner-table when I was in Germany at xmas. I'd recently found out at an [Edinburgh GeoMob](https://thegeomob.com/post/sept-30th-2025-geomobedi-details) talk by [Peter Creasey](https://www.linkedin.com/in/peter-creasey-9250962/) that Scotland had [freely-available Lidar datasets](https://remotesensingdata.gov.scot/data#/map). This sounded like a good opportunity to use them, particularly because I was wanting to play with datasets that provide height information.

<!-- more -->

The first hurdle at which so many of these "what if?" questions fall is access to data. So, a huge thanks to the Scottish Government for making these datasets available, and in an easily understood form! 

The Lidar datasets contain a [Digital Terrain Model](https://www.neonscience.org/resources/learning-hub/tutorials/chm-dsm-dtm) which looked like what I needed as input, so my rough plan was:
1. Find boundary of Edinburgh in [OvertureMaps](https://explore.overturemaps.org/?mode=explore&feature=divisions.division_area.58a34fa4-bc76-476e-81a8-1ed8a5cd693f#11.72/55.9108/-3.2636)
2. Find grid cells in Lidar data corresponding to this area
3. Build an H3 grid over same area
4. Map H3 grid over Lidar cells, extracting out the min heights that sit under it
5. Visualise impact of changing sea-level by display cells that sit under different heights

This for sure could be improved, but I find it is sometimes easier to do something concrete but imperfect, before improving it later or taking these learnings to subsequent projects.

One of the first things I noticed after a first-pass through doing all of the above was that the Edinburgh boundary seemed to exclude pieces of the coast:

{{ image(src="/images/edinburgh_heights/edinburgh_boundary2.png") }}

<br/>

This is a good example of how different aspects of geo quality can affect what you are doing in a very case-specific way. With my other [projects](/posts/2024-10-01/) where I've used this same boundary I've been using it for things like constraining placement of random points, so it hasn't mattered too much. In this case I explicitly care about the boundary close to the water. 

I decided to fudge it a little here by applying a buffer of 400 metres and manually inspecting it was sufficient to include my areas of interest. This isn't rigourous and wouldn't scale easily to other cities, but was good enough for this specific example.

{{ image(src="/images/edinburgh_heights/edinburgh_boundary_buffered2.png") }}

Building and using the grids ended up being a lot of back-and-forth between Claude/Opus4.5 and myself, either separately or via the [Marimo integration](https://marimo.io/features/feat-ai). Claude tended to produce a big wodge of Python for solving the whole thing. However, whilst I like Python, it's too easy for Claude, and myself, to make dumb mistakes. Add onto this that we're dealing with Geo, where you're only one bad projection away from making your result meaningless.

So, I used Claude's suggestions in a similar way as I do my own Geo incremental explorations: splitting steps into smaller functions and chunks, and using these incrementally in a notebook, inspecting the output as I go. For example, visualising the Lidar grid ...

The process of extracting the data takes about an hour, so I split this out into a [separate notebook](/notebooks/questions/edinburgh_heights/extract_edinburgh.html) which outputs a [GeoArrow](https://geoarrow.org) file in [Feather format](https://arrow.apache.org/docs/python/feather.html). If I were to do this again, I'd probably explore the [Zarr store over GeoTIFF](https://developmentseed.org/geozarr-examples/examples/cog-to-zarr/) option, as that may be more more efficient; this would probably replace steps 2 to 4, just with a different cell definition. One for next time 🙂.

I found [Kepler.gl](https://kepler-preview.foursquare.com) really useful as a way to play with this dataset and in particular to see where there may be interesting height cut-points. Note that the Arrow file needed to be saved as uncompressed, as Kepler doesn't yet supported compressed GeoArrow.

<br/>

Ultimately, I produced a summary in a [visualisation notebook](/notebooks/questions/edinburgh_heights/vis_edinburgh.html) which sliced at different heights, and then visually compared how this affected the area remaining:

{{ image(src="/images/edinburgh_heights/edinburgh_height_slices.png") }}

<br/>

My overall (simplistic) conclusion is that Edinburgh will not be hugely effected, especially if you consider that this is the buffered shape that already includes some sea area. This seems to be consistent with a more rigourous approach from [Climate Central](https://www.climatecentral.org/what-we-do) looking at, for example, [land projected to be below annual flood level in 2110](https://coastal.climatecentral.org/mapview/12/-3.2204/55.9412/014da2d18f83f88d1b0d3a9607fd1f41e21d47166f47d9cf1b00cb47bc60e86a) (red areas):

{{ image(src="/images/edinburgh_heights/year_2110_return_level_1_ssp3rcp70_p50_contiguous_ipcc_2021_med.png") }}

<br/>

This is obviously devastating for people who live in these areas, and I don't want to minimise that. I'm also sure that Edinburgh as a whole will experience many other negative climactic impacts, but looking purely at direct sea-level rise, it seems to be comparatively spared.
