# The size of an evaluation run in gold

*Investigation of 2026-11-17, with nothing built. It measures where an evaluation run's bytes go in
gold, and how far lossless layouts reduce them, for
[Phase 8 of the current slice](current-slice.md#phase-8-the-size-of-a-run-on-disk). What holds
after a choice belongs in `docs/medallion.md`. The rest goes stale.*

This doc covers the Parquet files an evaluation run writes to gold, and layouts that store the same
rows in fewer bytes. It is for whoever chooses how a run is stored, or builds the chosen layout.
Here, a lossless layout is one whose files rebuild the current rows exactly.

The findings hold for the 33 runs in gold on 2026-11-17. The measurements used
[polars](https://pola.rs/) 2.1.0, [pyarrow](https://arrow.apache.org/docs/python/) 26.0.1, and git
2.54.0. The arrow-rs `parquet` crate 57.3.1 wrote the runs.

## In brief

- In runs over all 34,521 sessions, transitions take 53–79% of a run's bytes, and outcomes most of
  the rest.
- An enum code per transition saves little. Parquet already stores each state as a small integer,
  and `from` repeats the previous `to`.
- Grouping each crossing's transitions into episodes, and ordering sessions by the crossings they
  pass, cuts transitions to a fifth or a quarter. The same order cuts outcomes to a third.
- Across the 33 runs, the files shrink from 430.6 MB to 111.7 MB. A git pack of them shrinks from
  327.5 MB to 84.3 MB.
- The current transitions and outcomes rebuild exactly from the new files.

## Method

A Python script read each run's files with polars, built each layout, and wrote it with pyarrow.
Unless a passage says otherwise, each file uses:

- the [zstd](https://github.com/facebook/zstd) codec at level 3, as the store's writer does
- row groups of 1,048,576 rows, the default of both writers
- dictionary encoding on every column

Rewritten this way, the current transitions of the largest run take 29.51 MB, against 29.42 MB as
the store wrote them. A size in MB counts 10⁶ bytes.

Two runs serve as cases throughout. Both replay the same 34,521 sessions:

| Run | Predictor | Reach | Half-width | Transitions | Outcomes |
|---|---|---|---|---|---|
| `731f0149` | LightCone | 20 km | 60° | 29.42 MB | 6.96 MB |
| `882111f4` | LightCone | 1 km | 45° | 8.07 MB | 2.96 MB |

`731f0149` is the largest run in gold. `882111f4` uses the settings chosen for the apps, scored on
the tune split.

A git measurement copies files into a new repository, commits each run separately, and runs
`git gc` with default settings. A pack's size is the size of its `.pack` file.

## Where a run's bytes go

Three datasets hold nearly every byte of `731f0149`:

| Dataset | Rows | Size |
|---|---|---|
| `evaluation_transition_v1` | 8,573,795 | 29.42 MB |
| `evaluation_outcome_v2` | 1,365,777 | 6.96 MB |
| `evaluation_session_v2` | 34,521 | 0.96 MB |

The run, summary, skew, and split datasets take 24 kB together.

Two columns take most of the transitions:

| Column | Share of transitions |
|---|---|
| `crossing_compact_id` | 46% |
| `at` | 41% |
| `to` | 5% |
| `from` | 5% |
| `session_id` | 3% |

The outcomes spread wider. `notified_at` takes 31%, `crossing_compact_id` 22%, `crossed_at` 17%,
`session_id` 11%, and `lead` 9%. `outcome`, `class`, and `score` take 3–4% each. In the sessions,
`session_id` takes 78%.

A run's size grows with the predictor's reach. Over the same sessions, LightCone writes about 29 MB
of transitions at 20 km, and about 8 MB at 1 km.

### In git

Over `main`, the branch's gold holds 329.8 MB of objects on disk. Transitions take 228.6 MB of it,
and the two outcome versions 99.1 MB.

In a pack, git stores an object either whole or as a delta against a similar object. It looks for
that object among neighbours in a list sorted by type, a hash of the path, and size
([`git pack-objects`](https://git-scm.com/docs/git-pack-objects)). Git finds no delta between the
current transitions of LightCone at 1 km and 45°, and at 1 km and 60°, even under
`git gc --aggressive`. The pair takes 16.1 MB as files and 14.7 MB packed.

Identical files cost one object. The 33 committed session files are 5 objects, since runs over one
pick write the same sessions. A tune run and a test run of one setting write the same transitions,
and share an object. So do three runs of CrowFlies at 1 km from 2026-11-10 and 2026-11-11.

## What the transitions repeat

Four properties of the data allow lossless layouts smaller than one row per transition. The counts
in this section come from `731f0149`.

### Each crossing's transitions form a chain

Within a session, each crossing's transitions form a chain. Each transition's `from` equals the
previous `to`, and the first `from` is `out_of_reach`. This holds for all 8,573,795 transitions.
`from` therefore carries nothing that `to` and the row order lack.

At one sample, the tracker emits at most two transitions for a crossing: into `alerted_pass`, then
into `actual_pass`. The run holds 4,767 such pairs.

### Chains split into episodes, which follow few paths

An episode is one stay of a crossing within the predictor's reach. It starts as the crossing leaves
`out_of_reach`. It ends as the crossing returns there, or as the session ends. An episode's path
lists the states it enters, in order.

The run holds 2,929,900 episodes, about 2.9 transitions each. They follow 169 distinct paths, with
an entropy of 3.0 bits per episode. Five paths cover 78% of episodes:

| Path | Episodes | What happens |
|---|---|---|
| `candidate_pass`, `out_of_reach` | 1,170,395 | comes within reach and leaves |
| `candidate_pass` | 711,274 | still within reach at the session's end |
| `candidate_pass`, `alerted_pass`, `candidate_pass`, `out_of_reach` | 161,784 | alerted, withdrawn, and leaves |
| `candidate_pass`, `alerted_pass`, `candidate_pass` | 127,722 | alerted and withdrawn, and still within reach at the end |
| `candidate_pass`, `alerted_pass`, `actual_pass`, `candidate_pass`, `out_of_reach` | 119,388 | alerted, passed, released, and leaves |

Of all episodes, 1,243,728 (42%) are still open at the end of their session.

### Times fall on a grid of samples

Every `at` lies a whole number of 10-second steps after its session's start. The grid comes from
the samples in silver, not from the code, so a layout cannot rely on it. No layout here needs it.
Offsets in milliseconds compress as well as counts of 10-second steps: 6.97 MB against 6.95 MB.

### Sessions repeat routes

Sessions on one route pass the same crossings in the same order. In the run:

- The 34,514 sessions with episodes follow 9,265 distinct sequences of crossings.
- Their episodes take 26,334 distinct forms. Sessions that exactly repeat another hold 16% of
  episodes.
- In silver's passes, its ground truth, 29,802 of the 34,521 sessions follow 3,944 distinct
  sequences of crossings.

## An enum for the states

Parquet's dictionary encoding stores each distinct value of a column chunk once, in a dictionary
page. Each row then holds an integer index into that page, bit-packed to the width the dictionary
needs ([Parquet encodings](https://parquet.apache.org/docs/file-format/data-pages/encodings/)). A
column of four state names therefore needs two bits per row before the codec runs.

On `731f0149`, the state columns take:

| States stored as | Size |
|---|---|
| `from` and `to`, as names | 2.90 MB |
| `to` alone, as names | 1.45 MB |
| `to` alone, as `u8` codes | 1.45 MB |
| one `u8` code for each `(from, to)` pair | 2.05 MB |

Names and codes cost the same, since the dictionary turns names into codes. A code for the pair
still stores `from`, which the chain makes redundant.

The enum pays at the scale of an episode. One path per episode, as a single dictionary-encoded
string, takes 1.09 MB in session order and 0.52 MB in route order. On `882111f4`, a path spelled
in full state names takes the same 0.08 MB as one spelled in letters. The dictionary holds each
distinct path once. A list of state names in place of one string takes 0.20 MB.

## Layouts for transitions

Each layout in this table stores every transition. The sizes cover transitions alone.

| Layout | `731f0149` | `882111f4` |
|---|---|---|
| One row per transition, as now | 29.42 MB | 8.07 MB |
| One row per transition, without `from`, with a session index and offsets | 22.19 MB | – |
| One row per sample, with a list of crossings and a list of states | 19.87 MB | – |
| One row per episode, sessions in index order | 14.78 MB | 2.58 MB |
| One row per episode, route order from the run's episodes | 6.94 MB | 1.49 MB |
| One row per episode, route order from the run's episodes, zstd level 19 | 5.89 MB | 1.18 MB |
| One row per episode, route order from silver's passes | 7.48 MB | 1.50 MB |

### One row per episode

An episode row holds:

- a session index, a dense integer that names a session within a pick
- `crossing_compact_id`
- the offset from the session's start at which the episode starts
- the path
- the gaps between the episode's consecutive transitions, as a list

`crossing_compact_id` then appears once per episode instead of once per transition. A gap within an
episode is a smaller number than an offset from the session's start. On `731f0149`, the crossings
shrink from 13.54 MB to 4.65 MB, and the times from 12.15 MB to 8.84 MB.

### Route order

Parquet compresses each page of a column on its own
([Parquet concepts](https://parquet.apache.org/docs/concepts/)). The codec therefore finds repeats
only among rows that share a page. Route order sorts sessions by the sequence of crossings they
pass, so sessions on one route sit side by side. Their crossings, offsets, paths, and gaps then
repeat within a page.

Two sources give the sequence:

- **The run's episodes.** Each session's crossings, in the order its episodes start. This order
  differs between runs.
- **Silver's passes.** Each session's crossings, in the order the train passes them, from
  `train_session_crossing_v1`. This order depends only on the pick, so every run over one pick
  shares it.

At 1 km, both sources give 1.49–1.50 MB. At 20 km, silver's passes give 7.48 MB against 6.94 MB.
The passes name only crossings a train crosses, and a reach of 20 km holds many more.

Other keys order sessions poorly. Ordering by `trip_id` gives 13.21 MB, and by source label and
start 13.41 MB, against 6.03 MB in route order. All three number crossings in the order they first
appear. The source label names only the feed, `gtfs.de`.

### Encodings, codecs, and types

On the episodes of `882111f4` in route order:

- With dictionary encoding on every column, as the store's writer does, the file takes 1.49 MB.
  Plain encoding for `crossing_compact_id` and the start offset gives the same size.
- With dictionary encoding off for every column, the file takes 1.45 MB.
- With offsets as `i64` durations, the file takes 1.74 MB, against 1.50 MB as `u32` milliseconds.
  The store writes a `TimeDelta` as an `i64` duration.
- With `session_id` in place of the session index, the file takes 2.04 MB, against 1.49 MB. On
  `731f0149`, `session_id` adds 0.64 MB.

Higher codec levels save more on episodes in route order than on other layouts:

| Layout | Codec | Saving against zstd level 3 |
|---|---|---|
| Current transitions of `731f0149` | zstd level 19 | 6% |
| Episodes of `731f0149`, index order | zstd level 9 | 3% |
| Episodes of `731f0149`, index order | zstd level 19 or 22 | 6% |
| Episodes of `731f0149`, index order | [Brotli](https://github.com/google/brotli) level 11 | 9% |
| Episodes of `731f0149`, route order | zstd level 19 | 15% |
| Episodes of `882111f4`, route order | zstd level 19 | 21% |

`DELTA_BINARY_PACKED` encoding made each layout larger: by 2% with one row per transition, and by 9%
with one row per episode. Ordering episodes by crossing before session made them larger as well:
17.44 MB against 14.78 MB.

Numbering crossings in the order they first appear, with sessions in route order, saves a further
13% at 20 km: 6.03 MB against 6.94 MB. Episodes that start at the same sample then sort in route
order. `crossing_compact_id` is the low four bytes of an MD5 of the crossing's ID
([crossings](../crates/crossings/README.md#ids-name-a-crossing-not-a-row)), so its order follows no
route. The crossing column then holds a per-run number, which needs a lookup table to name the
crossing.

## Outcomes

`lead` equals `crossed_at − notified_at` in every row of `731f0149`, `882111f4`, and `a029d5b6`. A
compact outcome row therefore holds:

- the session index
- `crossing_compact_id`
- `outcome`, `class`, and `score`
- `notified_at` and `crossed_at`, as offsets from the session's start

| Layout | `731f0149` | `882111f4` |
|---|---|---|
| As now | 6.96 MB | 2.96 MB |
| Compact rows, sessions in index order | 4.58 MB | 1.75 MB |
| Compact rows, route order from silver's passes | 2.48 MB | 1.05 MB |

With route order from the run's episodes, zstd level 19 saves a further 11–17%.

The outcome columns stay out of the episode file. `score` writes outcomes after `replay` writes
transitions, and gold refuses a second write of a run to a dataset.

## Every run, and git

Converted to episodes in route order from silver's passes, with compact outcomes, the 33 runs take:

| | Now | Episodes and compact outcomes |
|---|---|---|
| Transitions or episodes | 310.85 MB | 70.09 MB |
| Outcomes | 119.77 MB | 41.57 MB |
| All files | 430.62 MB | 111.66 MB |
| Git pack of all files | 327.51 MB | 84.31 MB |

A run of LightCone at 1 km takes 2.55 MB, against 11.03 MB now. A run at 20 km takes about 10 MB,
against about 36 MB. [Per-run sizes](#per-run-sizes) lists every run.

Across the 33 runs, packing saves 24% in both layouts. Identical files account for 17.5% of the
files now, and 14.4% in episodes. On the remaining files, git saves 7.8% now and 11.8% in episodes.

For one pair of runs, route order from silver's passes lets git find a delta. Of the episodes of
LightCone at 1 km and 60°, 83% match an episode at 1 km and 45°. Packed together, the 45° file
takes 1.42 MB, and the 60° file a delta of 0.65 MB. The pair takes 2.06 MB, against 14.70 MB for
its current transitions.

Without compression in Parquet, git finds more. The same pair packs to 1.74 MB, but each file takes
17.9 MB in a checkout, against 1.5 MB.

## Checks that the layouts are lossless

- Expanding the episodes of `731f0149`, and sorting by session, time, crossing, and position in the
  episode, gives the current transitions. The result equals the current file row for row, in
  order, across all 8,573,795 rows.
- Rebuilding outcomes from the compact rows of `882111f4` and `a029d5b6` gives exactly the current
  rows, every column included: 404,880 and 802,768 rows. The current outcome files follow no key
  order, and the rebuild does not reproduce their row order.

## Lossy alternatives

Each alternative in this list drops information that a checkout cannot recover.

- **No transitions in git.** This removes 79% of the largest run's bytes. `score` reads
  transitions, so rescoring a run from a checkout means replaying it against silver that has since
  changed.
- **No transitions between `out_of_reach` and `candidate_pass`.** This removes 54% of transitions.
  No score reads them, but they record the time each crossing came within reach.
- **Only entries into `alerted_pass`.** This keeps 21% of transitions, which the outcomes mostly
  repeat.

## Options

1. **Episodes and compact outcomes in route order, with a session index.** The pick computes the
   route order from silver's passes, and the session dataset records it as the session index.
   Every run over one pick shares that file. A run at 1 km takes a quarter of its current size.
2. **Option 1, with `session_id` in place of the session index.** A file then names its sessions
   without a join. The episodes of a run at 1 km take 0.55 MB more, and the outcomes carry the same
   dictionary of session IDs.
3. **One row per transition, without `from`, with offsets.** Readers change least, and transitions
   shrink by a quarter.
4. **A higher zstd level alone.** Level 19 saves 6% on the current layout. The store's writer uses
   one level for every layer.
5. **A lossy alternative.**

Option 1 makes runs smallest without losing a row. Option 2 trades 0.55 MB or more per run for
files that read without a join.

## What option 1 needs

- **Datasets.** An episode dataset replaces `evaluation_transition_v1`, beside
  `evaluation_outcome_v3` and `evaluation_session_v3`. "Visit" already names the online detector's
  count in `evaluation_skew_v2`, so the episode dataset needs another name.
- **Route order.** The pick reads each session's passes from silver, orders the sessions by them,
  and writes the session index into `evaluation_session_v3`.
- **Conversion.** One function groups transitions into episodes, and its inverse expands them. A
  property test checks the round trip. `score` and the notebooks read expanded transitions.
- **The path.** A newtype holds a path, and refuses an illegal transition at construction, as the
  state types do now. A path in full state names costs no more than one in letters, and reads
  without the code, as [gold](medallion.md#gold-1) asks of a run.
- **Offsets.** `u32` milliseconds cost 14% less than `i64` durations.
- **The writer.** No change. The saving comes from the layout and the row order, not from Parquet
  settings.
- **Migration.** The 33 runs move to the new datasets through the row types.

## Open questions

- What to call an episode.
- Whether a file names its sessions by index or by `session_id`.
- Whether gold writes at zstd level 19, for a further 15–21% on episodes in route order.
- Whether to number crossings by first appearance, for a further 13% at 20 km, at the cost of a
  lookup table per run.
- Whether the arrow-rs writer matches pyarrow's sizes for a list column. Only pyarrow wrote the
  files measured here.
- Whether the branch rewrites its history before it merges. [medallion.md](medallion.md#bronze)
  lets a branch that has not merged drop the bronze files of a version it both added and migrated.
  It states no such rule for gold. The branch's gold holds 329.8 MB on disk, superseded versions
  included, such as `evaluation_outcome_v1` at 29.2 MB.
- Whether to hold a run in `landing` until it is promoted. That decides which runs reach git,
  whatever their layout, and stays unmeasured.
