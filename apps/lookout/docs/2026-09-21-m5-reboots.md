# The device reboot loop

*Assessment of 2026-09-21, from one console log and a disassembly of the binary that
produced it. No fix has been tried and the cause is unknown. It records what the evidence
rules in and out, and what to measure next. Whatever survives a measurement belongs in
[`device.md`](device.md); the rest goes stale.*

The M5 shell reboots continuously, within seconds to two minutes of boot, on
`crux_core 0.16.2` — the version [`device.md`](device.md) records as stable. The pin held:
`Cargo.lock` carries 0.16.2, so that table row is now wrong.

## What crashes

The flashed image is the debug profile (`opt-level = "z"`, debug assertions on), ELF
`bd57b4a83`. Four signatures alternate across boots of that one binary:

| Signature | Where |
| --- | --- |
| `misaligned pointer dereference: address must be a multiple of 0x40 but is 0x3ffc5e20` | `crossbeam_channel::counter::Sender::counter` |
| `Guru Meditation Error: IllegalInstruction`, backtrace corrupt after one frame | `Command::done` |
| `unsafe precondition(s) violated: ptr::read requires that the pointer argument is aligned and non-null` | `std::thread` |
| `TG1WDT_SYS_RESET`, watchdog, PC in `_DoubleExceptionVector` | — |

Every readable backtrace reaches the same place:

```
Lookout::update → Command::new → CommandContext::clone → crossbeam Sender::clone → counter()
```

`Lookout::update` returns a `Command` for every event — `render::render()` where something
moved, `Command::done()` where nothing did. Both construct a `Command`, which allocates
five unbounded crossbeam channels, an `Arc`, a `Slab` entry, and a boxed future, then
clones the context. A dozen sentences a second therefore costs around sixty channel
create-and-drop cycles. The crashes follow events: the first sentence, or a battery tick at
62 or 122 seconds.

## What the evidence says

**The dereferenced pointer is garbage, not an under-aligned allocation.** `0x40` is
the alignment of `crossbeam_utils::CachePadded`, and `0x3ffc5e20` is 32-byte aligned. That
value is byte-identical on every boot, which fits deterministic garbage in a fixed location
rather than heap variation. It is the same shape as the `A2 = 0x00000000` null `&self`
already recorded in [`device.md`](device.md): the `Sender` **value** read out of
`Command::new`'s frame is wrong, whatever it points at.

**The alignment panic is a detector, not the defect.** Rust emits the check under debug
assertions only. A release build removes the panic and leaves the undefined behaviour, so
the fault reappears as the Guru Meditation alone. Keep debug assertions on.

## Ruled out

| Suspect | Evidence against |
| --- | --- |
| Main task stack overflow | High-water mark 9,996 bytes free of 49,152, so the stack never came within 10 KB of its bottom. The faulting address sits above the highest observed frame, in the heap. `CONFIG_FREERTOS_WATCHPOINT_END_OF_STACK` is enabled and silent. |
| The allocator returning under-aligned memory | Traced in the flashed ELF: a specialised `exchange_malloc` hardcodes size 256 and align 64 → `__rust_alloc` → `System::alloc` takes the over-aligned branch (`MIN_ALIGN` is 4 on xtensa-espidf) → `posix_memalign` → `heap_caps_aligned_alloc_default`. `heap_caps_aligned_check_args` rejects only zero and non-powers-of-two, so 64 is honoured or the call returns null. |
| Aligned allocations freed with plain `free` | `heap_caps_aligned_free` is deprecated in ESP-IDF 5.5 in favour of `heap_caps_free`; plain `free` on a `posix_memalign` block is correct there. |
| A `crossbeam-channel` version change | 0.5.16 in every historic lockfile, including the ones behind the clean 30-minute soaks. |
| A `crux_core` version change | The `=0.16.2` pin held. |

## What did change

- **The core gained a second effect.** `3b5a81de` made `Effect` a two-variant enum with
  `typegen`, added `notify_shell(GetCrossings)`, and made the model generic over `Shell`.
  The clean soaks predate it. Adding an enum variant does not corrupt memory, so this is a
  bisection point rather than a mechanism.
- **The toolchain is unpinned.** `rust-toolchain.toml` says `channel = "esp"`, currently
  `rustc 1.90.0-nightly (abf50ae2e 2025-09-16)` with GCC `esp-15.2.0_20250920`. The Xtensa
  backend has a recorded history of miscompiling Rust — a loop miscompilation fixed for
  Rust 1.65, alignment bugs with 128-bit arguments — and [`device.md`](device.md) already
  records `rustc` crashing inside `XtensaSizeReduce::ReduceMBB`. Pin it regardless of this
  bug.

## Prior art

crossbeam-channel 0.5.12 to 0.5.14 carried a double free in the unbounded (list) flavour: a
channel left half-initialised, then torn down, loading `head` without swapping it to null.
Fixed in 0.5.15, so 0.5.16 has the fix. Three things it establishes anyway:

- That bug produced garbage `crossbeam_channel::counter` pointers: a use-after-free shape,
  which is what this log shows, rather than an alignment one.
- Its trigger was **creating and dropping unbounded channels**, which is what a `Command`
  does five times per event.
- AddressSanitizer on the host found it, after 40 days of looking elsewhere.

## What to measure next

Ranked by information per unit of effort. The first two need no hardware, which is what
splitting the core from the shell bought.

1. **Miri over `platform-core`**, driving `Lookout::update` a few thousand times. It checks
   alignment, use-after-free, and aliasing, and it runs on crossbeam-channel — that crate's
   own tracker carries violations found this way. A clean run over thousands of iterations
   exonerates crux's logic and localises the fault to Xtensa; a failure names it outright.
   Miri does not model the ESP-IDF allocator, so it cannot see a fault in the allocator
   itself.
2. **AddressSanitizer on the host**, the precedent above. Slower to set up, runs the real
   allocator.
3. **A core dump.** `CONFIG_ESP_COREDUMP_TO_FLASH_OR_UART` in ELF format with
   `CONFIG_ESP_COREDUMP_CAPTURE_DRAM=y`, read back with `idf.py coredump-info`. This answers
   the question the panic printout cannot: whether `0x3ffc5e20` is a live heap block, a
   freed one, or not a block at all. That one fact splits the remaining hypotheses, and the
   corrupt backtraces become readable.
4. **Heap tracing in `HEAP_TRACE_ALL`**, started immediately before the first event, to name
   the allocation below the corrupted address.
5. **`heap_caps_check_integrity_all` around each `process_event`**, which narrows corruption
   to a single event. `esp_cpu_set_watchpoint` on the faulting address works here because the
   value is deterministic, but the ESP32 has two watchpoints and the stack-end watchpoint
   holds one.

## The design question underneath

A `Command` per event is expensive on this board, whatever the cause. It is also the
machinery every signature lands in. [`device.md`](device.md) lists dropping crux from the
shell as forfeiting the shared core. That is no longer the trade: `platform-core` abstracts
over `Shell`, and `platform/rerun-py` already drives the `predictor` state machine directly
without crux. The device can do the same and leave crux where a shared core earns its keep,
in the browser.
